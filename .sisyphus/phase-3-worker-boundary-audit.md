## Assumptions

### Current Thread and Ownership Boundary
- **Assumption:** Keep `SampleThread` responsible only for device reads and keep `tgraphcanvas.sample_processing()` as the GUI-owned state transaction; do not move `qmc` mutation, Qt calls, PID, alarms, events, or renderer application to the sampling thread.
  - **Why this way:** `SampleThread.sample()` gathers `temp1_readings`, `temp2_readings`, and `timex_readings`, then emits `sample_processingSignal` (`src/artisanlib/canvas.py:20893-20900`). `Athreadserver.createSampleThread()` connects that signal to `self.aw.qmc.sample_processing` with explicit `Qt.ConnectionType.QueuedConnection` (`src/artisanlib/canvas.py:20929-20937`). `sample_processing()` owns the `profileDataSemaphore`, rolling-buffer truncation, list append/backfill, state writes, and final `updategraphicsSignal` (`src/artisanlib/canvas.py:4770-4787`, `src/artisanlib/canvas.py:4954-5023`, `src/artisanlib/canvas.py:5535-5543`). Event signals are separately queued (`src/artisanlib/canvas.py:2739-2747`), and renderer mutation stays in `plot_live_frame.py` (`src/artisanlib/plot_live_frame.py:86-179`).
  - **If wrong:** Moving the whole slot or letting a worker touch `qmc` can race the GUI-owned lists and event indexes, duplicate or reorder samples, and call Qt/Matplotlib objects from the wrong thread.
  - **Confidence:** Confident

### Smallest Safe Worker Slice
- **Assumption:** The smallest safe next implementation is a single-flight worker boundary around the existing pure `build_live_processed_sample_frame()` call only. Treat it as a boundary proof, not a broad processing migration; keep smoothing/RoR, input filtering, math-expression evaluation, PID update, alarm evaluation, event side effects, and rendering in the current GUI transaction.
  - **Why this way:** `build_live_processed_sample_frame()` is already a pure function returning frozen `ProcessedSampleFrame` and only composes pure display/event/axis decisions (`src/artisanlib/sample_processing.py:972-1091`). Its current call site is a clean cut after the GUI has computed the current sample and RoR values and before the GUI consumes displayed deltas and event decisions (`src/artisanlib/canvas.py:5169-5198`). The output is already tested as an immutable contract (`src/test/unitary/artisanlib/test_sample_processing.py:2161-2324`, `src/test/unitary/artisanlib/test_sample_processing.py:2427-2475`).
  - **If wrong:** Workerizing smoothing/RoR first would require copying and versioning several mutable qmc histories, then splitting `sample_processing()` across an asynchronous response; late results could be applied to the wrong sample or cause semaphore/finally cleanup to run twice. Keeping the first slice to the existing frame helper limits the moved behavior to deterministic decisions.
  - **Confidence:** Likely

### Exact Worker Input, Output, and Signal Boundary
- **Assumption:** Send one immutable request object from GUI thread to a dedicated worker `QThread` with an event loop; return one immutable result object to a GUI-thread slot. Request fields must exactly cover the current helper inputs: `timestamp`, `sample_count`, `latest_et`, `latest_bt`, `smoothed_et`, `smoothed_bt`, `pid_process_value`, `raw_delta_et`, `raw_delta_bt`, `ror_limit_enabled`, `max_ror_limit`, `ror_limit`, `ror_limit_min`, `charge_index`, `dry_index`, `drop_index`, `delta_et_filter`, `delta_bt_filter`, `delta_et_samples`, `delta_bt_samples`, `fix_max_time`, `lock_time_x`, an immutable `sample_times` snapshot, `start_of_x`, `end_of_x`, `tp_alarm_timeindex`, `tp_max_roast_time`, `auto_charge_idx`, `auto_charge_flag`, `auto_charge_enabled`, `auto_drop_idx`, `auto_drop_flag`, `auto_drop_enabled`, and `mode`. Result must be the existing `ProcessedSampleFrame` fields: timestamp/count/latest ET/BT, smoothed ET/BT, PID process value, displayed Delta ET/BT, Delta ET/BT windows, live x-axis end, and `AutoEventDecisions` (`src/artisanlib/sample_processing.py:62-77`, `src/artisanlib/sample_processing.py:972-1103`).
  - **Why this way:** `sample_times` is read by the frame helper for charge-relative axis and event timing (`src/artisanlib/sample_processing.py:1018-1041`), so the worker must receive a tuple or equivalent immutable snapshot, never a live qmc list. The request signal must be queued GUI → worker; the result signal must be queued worker → GUI. Use a separate `QThread`, not `SampleThread`: `SampleThread.run()` overrides the thread entry point with a sampling loop and does not run a Qt event loop (`src/artisanlib/canvas.py:20862-20914`). The GUI result slot alone may append delta arrays, mutate event indexes, emit event signals, adjust axes, and call renderer code (`src/artisanlib/canvas.py:5198-5543`).
  - **If wrong:** Passing live lists permits post-submit mutation and non-deterministic frames. Using `SampleThread` as a queued worker can leave requests unhandled because its custom `run()` loop does not execute `QThread.exec()`. Applying the result in the worker would violate Qt affinity and move event/render behavior across the boundary.
  - **Confidence:** Confident

### Compatibility Risks and Required Focused Tests
- **Assumption:** Preserve strict single-flight ordering and current per-sample finalization before accepting the worker slice. Add focused worker-boundary tests; do not run or require broad GUI tests for this audit.
  - **Why this way:** `sample_processing()` currently acquires/releases `profileDataSemaphore` around the full transaction and always performs background playback cleanup plus `updategraphicsSignal.emit()` in `finally` (`src/artisanlib/canvas.py:4771-4787`, `src/artisanlib/canvas.py:5535-5543`). A worker response must carry a monotonic sequence and keep at most one request in flight; never silently discard an older result or release the semaphore twice. Existing pure-helper tests cover value contracts, while `test_plot_live_frame.py` covers renderer fallback and line/item mutation (`src/test/unitary/artisanlib/test_plot_live_frame.py:90-179`); no test currently proves a worker affinity or queued request/response boundary (`src/test/unitary/artisanlib` search for `sample_processingSignal`, `QueuedConnection`, and `SampleThread` has no matching test).
  - **If wrong:** Out-of-order responses can append the wrong displayed RoR, trigger a stale CHARGE/DROP/TP decision, or render a frame that no longer matches qmc state. Shutdown with an in-flight result can call a deleted receiver or strand the semaphore.
  - **Confidence:** Likely
  - **Focused tests needed:**
    - Direct equivalence: same request passed to the worker computation and `build_live_processed_sample_frame()` produces equal frozen `ProcessedSampleFrame`; request tuples remain unchanged.
    - Qt affinity/order: one request and one result cross a real `QThread` using queued signals; assert worker computation and GUI application run on their intended threads and sequence IDs remain ordered.
    - GUI continuation: fake qmc/canvas asserts PID update, alarm evaluator/state write, event signal emission, `apply_live_plot_frame()`, and `updategraphicsSignal` remain GUI-thread operations; assert one finalization per request.
    - Shutdown/overrun: stop with one request in flight and submit a second request; assert deterministic completion or explicit backpressure, never stale-result application or silent reorder.
    - Regression command: `cd src && .venv/bin/python -m pytest test/unitary/artisanlib/test_sample_processing.py test/unitary/artisanlib/test_plot_live_frame.py -q`.
